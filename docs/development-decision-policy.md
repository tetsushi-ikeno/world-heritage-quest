# 世界遺産クエスト 開発判断・フェーズ運営ルール

更新日: 2026-08-22

## 目的

この文書は、世界遺産クエスト開発で新しい気づき・改善案・方針変更が出たときに、
**「今対応するのか」「後のPhaseへ送るのか」**を一貫して判断するためのルールを定める。

個別Phaseの最新の目的・完了条件は [`development-roadmap.md`](./development-roadmap.md) を正本とする。
この文書では、Phaseをまたいで適用する判断原則を扱う。

---

## 1. 開発の基本原則

### 1-1. Phaseには目的と終了条件を置く

各Phaseでは、実装項目を増やし続けるのではなく、以下を明確にする。

- このPhaseで何を確定するか
- このPhaseで何をまだ作り込まないか
- どの状態になれば次のPhaseへ進めるか

Phaseの途中で新しいアイデアが出ても、すべてをその場で実装しない。
ただし、後から変更すると大きな手戻りになる構造上の問題は先送りしない。

### 1-2. 「後で変えたら今作っているものを作り直すか？」を最初に問う

新しい気づきが出たときの第一判断は次の一問とする。

> 後で変更した場合、今作っているものを大きく作り直すことになるか？

- **YES**: 現在のPhaseで検討・判断する
- **NO**: 原則バックログへ入れ、適切なPhaseで対応する

### 1-3. 大きな方向変更は、完成後ではなく早期に検証する

ゲームの基本体験、移動方式、画面遷移、状態管理、成長方式などに関わる違和感は、
「今の実装を完成させてから考える」のではなく、次のPhaseへ進む前に検証する。

一方で、視認性や演出など後から追加しやすい改善は、構造が固まる前に作り込みすぎない。

---

## 2. 新しい気づきの分類

新しい案・問題・違和感は、原則として A / B / C の3種類に分類する。

### A. Core / 構造変更

ゲーム全体の構造や基本体験に影響するもの。

例:

- エリア分割マップをやめて全国一枚マップにする
- 主人公中心の追従方式へ変更する
- 遺産の解放方式を変更する
- 研究センターの成長方式を変更する
- Golden Pathの順序を変更する
- セーブデータやゲーム状態の持ち方を変更する
- 画面遷移方式を変更する

**扱い:** 原則として現在のPhaseで立ち止まって検討する。

Aを後回しにすると、その後に作る画面・データ・コンテンツまで作り直す可能性が高いため、先送りしない。

### B. Feature / 追加機能

ゲームの基本構造を壊さず、独立して追加できる機能。

例:

- 遺産図鑑
- 称号
- 新しいクイズ形式
- 登録基準クイズ
- マップ上の検索・絞り込み
- 調査記録の追加機能

**扱い:** いったんバックログへ登録し、該当する機能PhaseまたはPhase Gateで採否を判断する。

その場の思いつきで実装を開始しない。

### C. UX / UI / 演出改善

ゲームの構造を変えず、分かりやすさ・楽しさ・見た目を改善するもの。

例:

- 未アクション対象に `!` を表示する
- 調査済み対象を見分けやすくする
- 主人公の輪郭を強調する
- 背景のコントラストを下げる
- ボタンや文字を大きくする
- ピラミトンの表情差分
- 発見アニメーション
- 効果音・BGM

**扱い:** 現在のPhaseがUI/UX検証Phaseでない限り、原則バックログへ送る。

ただし、操作不能・誤操作多発・次の行動が分からないなど、Golden Pathを成立させないUX問題はAに格上げして現在Phaseで対応する。

---

## 3. 「今判断するべきか」の4つの確認項目

A/B/Cの判断に迷った場合は、次の4点を確認する。

### 3-1. 後から変更すると手戻りが大きいか

影響範囲が以下に広がる場合は早期判断する。

- マップ
- 移動処理
- カメラ
- 状態管理
- セーブデータ
- 世界遺産データ
- チュートリアル
- 複数画面の遷移

### 3-2. Golden Pathが変わるか

プレイヤーがゲーム開始から主要体験へ到達するまでの流れが変わる場合は、現在Phaseで検討する。

### 3-3. データ構造・状態管理に影響するか

以下のような状態を新しく持つ必要がある場合は、早期に判断する。

- 発見済み / 未発見
- 遺産ごとの研究進捗
- 研究センターのレベル
- 調査済み対象
- 問題履歴
- プレイヤー位置
- 解放状態

### 3-4. ゲームの面白さの仮説そのものに関係するか

このゲームの中心体験である、

**日本を旅する → 世界遺産を発見する → 調査する → 知識を得る → 次の行動へ進む**

という循環そのものに影響する場合は、見た目の問題ではなくCore問題として扱う。

## 4. Phaseごとのレビュー方法

### Phase開始時: Design Check

Phaseに着手する前に確認する。

1. このPhaseで確定させるものは何か
2. 完了条件は何か
3. 後から大きく変更しそうな前提が残っていないか
4. このPhaseでは作らないものは何か

### Phase途中: Core Issue Review

開発途中でA分類の問題が見つかった場合のみ、通常作業をいったん止めて判断する。

「今の仕様のまま完成させても後で作り直す」と分かっている状態で進めない。

B/C分類は原則としてバックログへ送り、現在Phaseの目的を守る。

### Phase終了時: Phase Gate

次のPhaseへ進む前に以下を確認する。

1. Phaseの終了条件を満たしたか
2. Golden Pathが最後まで通るか
3. 実際に操作して構造上の違和感がないか
4. 次Phaseへ持ち越してはいけないCore問題が残っていないか
5. 新しく出たアイデアをA/B/Cに分類したか
6. 次Phaseへ送るバックログを整理したか

---

## 5. Core Design Freeze

構造検証を行う初期〜中期Phaseでは、必要であれば大きな方針変更を許容する。

一方、全国展開・コンテンツ量産へ入る前には **Core Design Freeze** を置く。

Freeze対象の例:

- 全国マップ方式
- 主人公の移動方式
- 遺産発見方式
- 研究センターの基本構造
- 研究センター成長方式
- 学習ループ
- 基本画面遷移
- ゲーム状態管理
- セーブデータ構造

Freeze後は、重大なユーザーテスト結果や進行不能などを除き、これらを原則変更しない。

正確なFreezeのタイミングは、最新の [`development-roadmap.md`](./development-roadmap.md) で管理する。

## 6. Phaseの役割分担の考え方

具体的なPhase番号はロードマップを正とするが、開発順序は原則として次の考え方を守る。

1. **骨格を作る**
   - 状態管理
   - 移動
   - 画面遷移
   - Golden Path

2. **コア体験を成立させる**
   - 発見
   - 調査
   - 学習
   - 成長
   - 再訪

3. **複数遺産・全国へ拡張できる構造にする**
   - 遺産ごとの状態
   - データ駆動化
   - セーブ構造

4. **学習・問題システムを拡充する**
   - 過去問
   - 独自問題
   - 登録基準
   - 並べ替え等の問題形式

5. **全遺産へコンテンツ展開する**
   - 構造が固まってから量産する

6. **UI / UX / 演出を仕上げる**
   - 視認性
   - 操作性
   - 表情・アニメーション
   - 音

7. **QA・バランス・永続化を仕上げる**

8. **実ユーザーテストを行う**

9. **v1.0として公開する**

重要なのは、**大量のコンテンツを作る前にCoreを固めること**である。

## 7. バックログ運用

新しい案は「今実装する / 忘れる」の二択にしない。

最低限、以下を記録する。

| 項目 | 内容 |
|---|---|
| アイデア / 問題 | 何に気づいたか |
| 分類 | A: Core / B: Feature / C: UX |
| 影響範囲 | マップ、研究センター、問題、セーブ等 |
| 対応時期 | 今対応 / 次Phase Gate / 将来Phase |
| 判断理由 | なぜ今やる、または後回しにするのか |

### 例

| アイデア / 問題 | 分類 | 対応 |
|---|---|---|
| 4エリア分割より全国一枚マップの方が日本を旅する体験に合う | A | 現在Phaseで検証・決定 |
| 未アクション対象に `!` を付ける | C | UI/UX検証Phaseで検討 |
| 登録基準の並べ替え問題 | B | 学習・問題機能を扱うPhaseで採否判断 |
| 主人公が背景に埋もれて次の操作が困難 | C → A | Golden Pathに影響するなら即対応 |

---

## 8. Labを使う判断

大きな変更を本編へ直接入れない。

原則として次の順で進める。

**気づき → A/B/C分類 → 必要ならLabで単機能検証 → APPROVED → 本編統合 → Golden Path確認 → Main反映**

特にA分類の変更は、可能な限りLabで操作感を確認してから本編へ統合する。

---

## 9. この文書の使い方

別チャットや別作業で開発を再開するときは、以下の順で確認する。

1. [`development-roadmap.md`](./development-roadmap.md) で現在Phaseと終了条件を確認
2. 本文書で新しい気づきの扱いを確認
3. Aなら現在Phaseで判断
4. B/Cならバックログへ送り、現在Phaseの目的を守る
5. Phase Gateを通してから次Phaseへ進む

このルール自体を変更する必要が出た場合は、その理由を明記して本文書を更新する。
